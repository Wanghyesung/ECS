# Unity Architecture Refactor

목표는 기존 구조를 보존하거나 새 기술을 도입하는 것이 아니라, 요구사항을 만족하면서 전체 유지 비용이 가장 낮은 구조를 선택하는 것이다. 코드량 감소는 판단 요소 중 하나일 뿐 목표가 아니다.

## 모드

- `audit` — 기본값. 코드를 수정하지 않고 구조, 의존성, 수명, 변경 비용을 조사한다.
- `compare` — 현재 구조와 대체 기술·아키텍처를 근거로 비교한다.
- `plan` — 승인 가능한 작은 전환 단위, 검증, 롤백 계획을 작성한다.
- `refactor` — 사용자가 명시적으로 요청하거나 승인한 범위만 구현한다.
- `review` — 현재 diff가 구조를 실제로 개선했는지, 새 간접 계층이나 기술 부채를 만들었는지 검토한다.

사용자가 모드를 지정하지 않으면 `audit`으로 시작한다. 분석 요청은 구현 권한으로 해석하지 않는다.

## 시작 시 파싱

1. 저장소의 `AGENTS.md`와 관련 규칙·설계 문서를 읽는다. 규칙 내용을 이 스킬에 복제하지 않는다.
2. 관련된 기존 스킬·에이전트·설정이 있으면 재사용 지점만 확인한다. 모든 스킬을 무조건 읽지 않는다.
3. 패키지 매니페스트, asmdef, 부트스트랩, 씬 경계, 주요 호출부를 확인한다.
4. Git 상태를 확인하고 기존 사용자 변경을 작업 범위와 구분한다.
5. 현재 규칙을 다음처럼 분류한다.
   - 안전·플랫폼·직렬화 등 반드시 지킬 제약
   - 현재 채택한 기술·아키텍처 결정
   - 스타일과 관례

더 나은 후보가 현재 기술 결정과 충돌하면 후보를 조용히 제외하거나 규칙을 무시하지 않는다. 기대 이득, 전환 비용, 영향 범위와 함께 **정책 변경안**으로 보고하고 승인 전에는 구현하지 않는다.

## 조사 원칙

- 클래스 크기, 파일 수, 매니저라는 이름만으로 문제를 판정하지 않는다.
- 실제 호출 관계, 상태 소유자, 생성·폐기 주체, 씬 전환, 직렬화 참조, 이벤트·비동기 수명, 테스트 경계와 변경 파급을 추적한다.
- 인터페이스는 큰 클래스를 나누기 위한 장식이 아니다. 소비자 계약, 교체 가능한 구현, 외부 경계, 테스트 대체 지점처럼 실제 변경 축이 있을 때만 제안한다.
- 싱글톤은 개수만 세지 않는다. 애플리케이션·세션·씬·런·전투·GameObject 중 실제 수명과 전역 접근이 일치하는지 본다.
- 추상화나 서드파티 도입은 제거되는 복잡도와 새로 생기는 복잡도를 함께 계산한다.

상세 후보 비교와 판단 기준은 [decision-framework.md](references/decision-framework.md)를 읽는다.

## 기술 중립성

현재 사용하는 DI, 반응형 라이브러리, 풀, 비동기 도구, Addressables, 이벤트 시스템은 기본적으로 존중하되 정답으로 가정하지 않는다. 유지, 국소 대체, 단계적 제거, 전면 교체를 모두 후보로 둘 수 있다.

서드파티 후보를 검토할 때는 사용 가능한 Context7 또는 공식 문서로 현재 API와 Unity 버전 호환성을 확인한다. 기억만으로 패키지 API·수명 모델·등록 방식을 제안하지 않는다. 문서를 확인할 수 없으면 그 한계를 보고하고 구현 후보로 확정하지 않는다.

## 변경 절차

`audit`과 `compare`에서는 파일을 수정하지 않는다. `plan`은 한 번에 되돌릴 수 있는 bounded scope로 나누고, 각 단계에 동작 기준·검증·롤백을 둔다.

`refactor`에서는 다음을 지킨다.

1. 저장소의 코드 수정 전 조사 규칙과 관련 전문 스킬을 적용한다.
2. 승인된 한 범위만 수정한다. 저장소 전체를 한 번에 재작성하지 않는다.
3. 공개 동작과 직렬화 계약을 먼저 고정하고 구조를 바꾼다.
4. 새 인터페이스·서비스·이벤트·패키지는 구체적인 소비자와 제거되는 결합을 명시한다.
5. 컴파일과 관련 테스트를 통과한 뒤 다음 범위로 넘어간다.
6. 실패하면 원인을 구조 변경과 기존 환경 문제로 구분하고 무리하게 계속 확장하지 않는다.
