# Architecture Decision Framework

## 1. 문제를 증거로 정의한다

구조 문제는 다음 중 실제 영향이 확인될 때 기록한다.

- 변경 하나가 관련 없는 여러 파일로 전파된다.
- 의존성이 static 접근, 검색, 숨은 생성으로 선언부에 드러나지 않는다.
- 상태의 소유자나 생성·폐기 주체가 불명확하다.
- 애플리케이션, 씬, 런, 전투, 오브젝트 수명이 섞인다.
- 테스트가 Unity 씬이나 전역 상태 없이 실행될 수 없다.
- 동일 책임이 중복되거나 서로 다른 책임이 같은 변경 이유 없이 묶였다.
- 직렬화, 이벤트, 비동기, 풀 재사용 경계에서 상태가 누수된다.
- 프로파일이나 호출 빈도로 확인되는 성능 비용이 있다.

“클래스가 크다”, “싱글톤이 많다”, “패턴과 다르다”만으로는 충분한 근거가 아니다.

## 2. 후보를 비교한다

문제에 맞는 후보만 선택하되, 초기에 다음 범주를 빠뜨리지 않는다.

1. 요구 자체 제거 또는 책임 축소
2. 현재 구조의 작은 수정
3. Unity 기본 기능
4. 이미 설치된 패키지나 프로젝트 패턴
5. Context7 또는 공식 문서로 검증한 서드파티
6. 작은 자체 구현
7. 기존 기술 제거 또는 아키텍처 교체

첫 번째로 동작하는 후보를 자동 선택하지 않는다. 단순성, 위험, 장기 비용을 비교한 뒤 가장 작은 **총비용**의 후보를 고른다.

## 3. 총비용 기준

근거가 있는 항목만 상대 비교한다. 정밀하지 않은 숫자 점수는 만들지 않는다.

- 요구사항과 현재 동작 보존
- 의존 방향과 변경 파급
- 생성·폐기·씬 전환 수명
- 프레임 비용, 할당, 메모리
- Unity 직렬화와 에셋 참조 안정성
- 테스트와 디버깅 가능성
- 팀 학습·운영 비용
- 패키지 호환성, 유지보수, 라이선스 위험
- 마이그레이션 기간과 병행 구조 비용
- 실패 시 롤백 가능성

새 기술이 코드 몇 줄을 줄여도 Composition Root, 어댑터, 등록, 디버깅, 교육 비용이 더 크면 선택하지 않는다. 반대로 기존 기술을 유지하는 비용이 더 크면 이미 사용 중이라는 이유만으로 보존하지 않는다.

## 4. 인터페이스 판단

인터페이스는 다음 중 하나가 구체적일 때 유효하다.

- 현재 둘 이상의 구현을 교체한다.
- 플랫폼, 저장소, 네트워크, Unity API 같은 외부 경계를 격리한다.
- 소비자가 구현 전체가 아닌 안정된 계약에 의존해야 한다.
- 테스트에서 느리거나 전역적인 구현을 대체해야 한다.
- 서로 다른 배포·수명·변경 주기를 가진 모듈의 경계다.

구현이 하나이고 교체·경계·테스트 요구가 없다면 구체 타입 주입이나 직접 참조를 우선한다. 클래스 크기는 인터페이스 도입 근거가 아니다. 큰 클래스는 먼저 상태와 변경 이유를 기준으로 책임을 조사한다.

## 5. 싱글톤과 DI 판단

각 싱글톤을 애플리케이션, 세션, 씬, 런, 전투, GameObject 수명으로 분류한다.

다음이 확인되면 전역 접근 제거를 우선 검토한다.

- 실제 수명이 전역이 아니다.
- 여러 인스턴스나 병렬 실행이 필요하다.
- 호출부가 실제 의존성을 숨긴다.
- 초기화 순서가 암묵적이다.
- 테스트 간 static 상태가 누수된다.
- 기능 시스템이 다른 전역 매니저를 연쇄 호출한다.

해결책은 DI 컨테이너로 한정하지 않는다. `[SerializeField]` 직접 참조, 명시적 초기화 메서드, 수동 Composition Root, 생성자 주입, 씬 컨텍스트, DI 컨테이너를 비교한다. 컨테이너는 객체 그래프와 수명 관리의 복잡도가 수동 연결 비용을 넘어설 때 제안한다.

## 6. 기존 기술 교체 판단

반응형 스트림, 풀, 비동기 라이브러리, Addressables 같은 기존 기술도 다음을 확인한다.

- 해결하려던 문제가 아직 존재하는가?
- 해당 기능의 규모와 호출 빈도에 비해 복잡하지 않은가?
- 수명과 상태 소유를 더 명확하게 만드는가?
- 더 단순한 Unity 또는 C# 기능으로 같은 계약을 만족할 수 있는가?
- 제거 비용보다 유지 비용이 큰가?

현재 프로젝트 규칙이 기술 사용을 강제하면 구현 전에 규칙 변경 승인이 필요하다. 제안에는 수정해야 할 규칙 파일과 단계적 마이그레이션 경계를 포함한다.

## 7. 서드파티 검증

서드파티 후보마다 최소한 다음을 확인한다.

- 대상 Unity 및 C# 버전 지원
- Windows·모바일 등 실제 타깃 지원
- 설치·업데이트·제거 경로
- 객체 수명과 Unity 생명주기 통합 방식
- AOT/IL2CPP, stripping, 직렬화 영향이 관련되는지
- 공식 문서로 확인한 API와 예제
- 기존 패키지와 역할이 중복되는지

문서 확인 결과와 추론을 구분한다. 도입 전 작은 수직 슬라이스와 제거 가능한 롤백 경로를 계획한다.
