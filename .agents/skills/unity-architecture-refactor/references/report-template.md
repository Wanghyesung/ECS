# Architecture Audit Report

## 범위와 기준선

- 조사한 시스템·씬·폴더
- 현재 사용자 동작과 보존해야 할 계약
- 읽은 프로젝트 규칙과 관련 패키지
- 조사에서 제외한 범위

## 현재 구조

- 진입점과 실행 순서
- 상태 소유자
- 생성·폐기 주체와 실제 수명
- 외부 시스템과 직렬화 경계
- 명시적 의존성과 숨은 의존성

세 컴포넌트 이상의 실행 순서나 수명 관계가 복잡할 때만 작은 다이어그램을 사용한다.

## 발견 사항

각 항목을 다음 형식으로 작성한다.

### 문제명

- **근거**: 실제 파일·타입·호출 관계
- **영향**: 버그, 변경 파급, 성능, 테스트, 운영 중 무엇에 영향을 주는지
- **수명/소유권**: 문제가 발생하는 경계
- **위험도**: 높음·중간·낮음과 이유
- **지금 고칠 필요**: 즉시, 다음 변경 시, 관찰, 수정하지 않음

문제마다 관련 있는 후보만 비교한다.

| 후보 | 장점 | 새 비용·위험 | 정책 충돌 | 결론 |

| Unity/설치 패키지 |  |  |  |  |
| 검증된 서드파티 |  |  |  |  |
| 자체 구현/구조 교체 |  |  |  |  |

추천안을 하나 선택하고 선택하지 않은 후보의 탈락 이유도 짧게 적는다. 현재 규칙과 충돌하면 구현안이 아니라 정책 변경안으로 표시한다.

## 단계적 계획

각 단계는 독립적으로 검증하고 롤백할 수 있어야 한다.

1. 대상과 변경 경계
2. 유지할 공개 동작·직렬화 계약
3. 수정 파일과 마이그레이션 방식
4. 컴파일·테스트·Play 검증
5. 성공 조건과 롤백 방법

## 보류 사항

- 증거가 부족한 가설
- 현재 요청 범위 밖 문제
- 사용자 결정이나 정책 변경이 필요한 항목
- 도입 전에 추가 문서·프로파일 확인이 필요한 기술
