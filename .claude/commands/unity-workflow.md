# /unity-workflow — 전체 개발 파이프라인

다음에 대한 완전한 개발 워크플로우를 오케스트레이션합니다: **$ARGUMENTS**

이 커맨드는 4단계 파이프라인을 실행합니다: **명확화(Clarify) → 계획(Plan) → 실행(Execute) → 검증(Verify)**. 각 단계는 다음 단계로 넘어가기 전에 명시적인 사용자 확인이 필요합니다.

## 1단계: 명확화

완전한 요구사항 그림을 그리기 위해 사용자를 인터뷰합니다. 다음을 질문합니다:

1. **핵심 메커닉 / 기능의 목적** — 무엇을 하나요? 어떤 문제를 해결하나요?
2. **대상 플랫폼** — 모바일(iOS/Android), 데스크톱, WebGL, VR?
3. **성능 제약** — 목표 FPS는? 메모리 예산은? 드로우 콜 제한은?
4. **관련된 Unity 서브시스템** — 물리? UI? 애니메이션? 오디오? 네트워킹?
5. **통합 지점** — 이것이 어떤 기존 시스템과 맞닿아 있나요?
6. **완료 기준** — 완료되었다는 것을 어떻게 알 수 있나요? 무엇을 테스트해야 하나요?

모든 답변을 통합한 **요구사항 요약**을 작성합니다. 진행하기 전에 사용자에게 확인을 요청합니다.

사용자가 `$ARGUMENTS`에 상세한 설명을 제공했고 요구사항이 명확하다면, 각 질문을 개별적으로 하는 대신 요약을 바로 제시하여 확인받아도 됩니다.

## 2단계: 계획

확정된 요구사항을 바탕으로:

1. **프로젝트 스캔** — 빠른 코드베이스 탐색을 위해 `unity-scout`(haiku)을 사용합니다: CLAUDE.md를 읽고, 관련된 기존 스크립트를 찾고, 어셈블리 구조를 매핑합니다
2. **서브시스템 식별** — 어떤 Unity 패키지와 스킬이 관련되어 있나요?
3. **모델 라우팅(model-routing) 스킬의 휴리스틱을 사용하여 복잡도 평가**:
   - 생성/수정이 필요한 파일 수를 추정합니다
   - 작업 설명에서 복잡도 키워드를 확인합니다
   - 위험 요소를 식별합니다(직렬화 변경, 네트워킹, 플랫폼 특화, 스레딩)
   - **간단**(1~2개 파일, 위험 없음) / **보통**(3~8개 파일, 일부 위험) / **복잡**(9개 이상 파일, 높은 위험)으로 등급을 매깁니다
4. **복잡도에 따라 실행 전략을 선택**합니다:
   - **간단** → `unity-coder-lite` (sonnet) — 더 빠르고 저렴함
   - **보통** → `unity-coder` (opus) — 더 깊은 추론
   - **복잡** → `/unity-team`을 통한 다중 에이전트
   - **전문화** → 도메인 에이전트로 라우팅: `unity-prototyper`, `unity-ui-builder`, `unity-network-dev`, `unity-shader-dev`
5. **구현 계획 생성**:
   - 생성/수정할 스크립트(파일 경로 및 어셈블리 배치 포함)
   - 필요한 씬 변경 사항(GameObject, 컴포넌트, 물리 레이어)
   - 기존 시스템에 대한 의존성
   - 위험 영역(직렬화, 플랫폼 특화, 성능)
   - 추정 복잡도와 근거를 포함한 선택된 에이전트 등급

계획을 사용자에게 제시하고 실행 전에 승인을 기다립니다.

## 2b단계: 크리틱 리뷰 (선택 사항)

원래 인자에 `--no-critic`이 지정되지 않은 한:

1. 승인된 계획과 함께 **`unity-critic`**(opus, 읽기 전용)을 호출합니다
2. 크리틱은 Unity 특유의 함정, 놓친 엣지 케이스, 과도한 엔지니어링, 성능 위험에 대해 계획에 이의를 제기합니다
3. 크리틱의 이의 제기 내용을 사용자에게 제시합니다
4. 실행 전에 타당한 이의 사항을 계획에 반영합니다
5. 심각한 이의 제기가 없으면 바로 3단계로 진행합니다

## 3단계: 실행

승인된 계획을 따릅니다:

1. **계획에 따라 적절한 에이전트로 라우팅**합니다
2. **`.claude/rules/`의 모든 규칙을 따르며 C# 코드를 작성**합니다
3. 필요하면 MCP를 통해 **씬 요소를 설정**합니다(속도를 위해 `batch_execute` 사용)
4. 각 주요 단계 이후 컴파일 오류를 확인하기 위해 `read_console`을 통해 **콘솔을 확인**합니다
5. 오류가 발견되면 진행하기 전에 수정합니다

자연스러운 이정표에서 진행 상황을 보고합니다(예: "스크립트 작성 완료, 이제 씬 설정 중...").

## 4단계: 검증

`unity-verifier` 에이전트를 실행하여 검증-수정 루프를 수행합니다:

1. unity-reviewer 체크리스트에 따라 변경된 모든 파일을 **리뷰**합니다
2. 자동으로 안전하게 수정할 수 있는 문제를 **자동 수정**합니다
3. 수정이 적용된 경우 **재검증**합니다(최대 3회 반복)
4. 가능하면 MCP를 통해 **테스트를 실행**합니다

### Deslop 패스(불필요한 코드 정리)

중대한 문제 없이 검증이 성공한 후, 이 워크플로우 중 생성되거나 수정된 모든 파일에 대해 표적화된 코드 비대화 검토를 수행합니다. 구체적으로 다음을 대상으로 합니다:

1. **불필요한 추상화** — 구현체가 하나뿐인 인터페이스, 하나의 타입만 생성하는 팩토리 클래스, 아무 동작도 추가하지 않는 래퍼 클래스
2. **과도한 주석** — 코드를 그대로 반복하는 주석, 당연한 내용의 문서 주석, 주석 처리된 코드 블록
3. **불필요한 오류 처리** — 그냥 다시 던지기만 하는 try/catch, 절대 null이 될 수 없는 값에 대한 null 체크, 그럴듯한 실패 시나리오가 없는 방어적 코드
4. **죽은 코드** — 사용되지 않는 private 메서드, 도달할 수 없는 분기, 사용되지 않는 매개변수
5. **과도한 엔지니어링** — 일반적이지 않은 문제에 대한 범용적인 해법, 성급한 최적화 패턴, 불필요한 디자인 패턴

Deslop 규칙:
- 단순화만 하고, 절대 복잡성을 추가하지 않습니다
- 런타임 동작을 모두 보존합니다
- 이 워크플로우가 시작되기 전부터 존재했던 코드는 건드리지 않습니다
- 의심스러우면 그대로 둡니다 — 거짓 양성(false positive)은 놓친 비대화보다 더 나쁩니다
- 수정 사항을 직접 적용한 뒤, `read_console`을 통해 콘솔을 다시 확인하여 회귀가 없는지 확인합니다

### 최종 요약

사용자에게 완전한 요약을 제시합니다:

```
## Workflow Complete

### What was built
- [list of features implemented]

### Files created/modified
- [file paths with brief descriptions]

### Verification results
- [auto-fixed issues]
- [remaining items for human review]

### Test results
- [compilation status, test pass/fail counts]

### Manual steps needed
- [any inspector assignments, scene references, etc.]

### How to test
- [step-by-step testing instructions]
```

## 설계 원칙

- **각 단계 게이트는 사용자 확인을 필요로 합니다** — 절대 건너뛰지 않습니다
- **기존 패턴을 우선합니다** — 프로젝트에 확립된 관례를 따릅니다
- **최소 실행 가능한 구현** — 첫 번째 패스에서 과도하게 만들지 않습니다
- **모든 것을 검증합니다** — 검증 단계는 선택 사항이 아닙니다
